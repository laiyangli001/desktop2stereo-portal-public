# 订单号规则 V1.0

本规则采用用户最终确认的16位方案，取代此前的12位按日流水草案。

1. 订单号固定为16位，仅允许数字0-9。
2. 订单号结构：YYMMDDHHMMSS + 4位秒内流水号。
3. 前12位为订单生成时间，格式YYMMDDHHMMSS，统一使用Asia/Shanghai时区。
4. 后4位为同一秒内自增流水，范围0001-9999，左补0。
5. 流水号按“秒”重置，即每秒从0001开始。
6. 订单号生成必须通过Redis原子INCR或数据库序列保证唯一。
7. Redis Key建议为order:seq:YYMMDDHHMMSS，过期时间建议1小时。
8. 同一秒流水超过9999时，抛出异常，不允许生成重复订单号。
9. 订单号生成后不可修改、不可复用。
10. 数据库订单表必须对order_no建立唯一索引作为最终兜底。
11. 服务器必须启用NTP时间同步，禁止手动回拨系统时间。

## 示例

| Asia/Shanghai时间 | 秒内顺序 | 订单号 |
|---|---|---|
| 2026-05-18 14:30:25 | 第1单 | 2605181430250001 |
| 2026-05-18 14:30:25 | 第2单 | 2605181430250002 |
| 2026-05-18 14:30:26 | 第1单 | 2605181430260001 |

## 本项目实现约束

当前选用MySQL数据库序列方案，不依赖Redis。第7条仅为Redis替代方案的命名建议，不表示本站已经使用Redis或会在1小时后删除数据库计数。若以后改用Redis，不能在Key过期、重建或切换后从0001重新分配同一秒的号码；仍须保持不可复用及数据库唯一约束。

使用独立InnoDB事务按UTC秒键锁定计数行，以固定Asia/Shanghai时区格式化订单时间；每个新秒建立新计数，旧计数不清除。号码与内部订单ID的映射在独立事务提交，业务建单失败或回滚仍保留，允许跳号，禁止回退和复用。不同应用实例共享数据库计数，不用进程内变量代替序列。

迁移 `0025_order_number_clock.php` 新增单行持久化高水位 `portal_order_number_clock`。每次新发号在独立事务中锁定该行，并拒绝比最后成功发号时间回退超过 `D2S_ORDER_CLOCK_MAX_ROLLBACK_SECONDS`（默认5秒，允许0～86400）的新请求，返回 `order_number_clock_rollback`。已有订单号的幂等重试先返回原号，不因之后时钟回拨而失败。该门禁只能阻断应用层明显回拨，不能证明主机已连接可信NTP。

portal_orders.order_no为CHAR(16)并建立唯一索引；独立只追加映射通过外键与订单绑定，UPDATE触发器禁止修改订单号。内部关联ID不等同于对外业务订单号。新单始终写入order_no；旧单保持原关联，不回填伪造生成时间或修改已提交支付单号。

所有接口和前端将订单号按字符串处理，禁止转成浮点数或JavaScript Number。退款号、支付平台交易号、内部关联ID分别保留，不用订单号冒充其他标识。两位年份当前支持2000～2099年，跨世纪前须升级编号规则，不能复用既有编号。

同秒第10000次分配返回order_number_capacity_exceeded，业务不得创建无号订单，也不将时间改为下一秒伪造成功。用户或后台可在下一次请求按真实服务端时间重试。

## 部署与回滚要求

- 在独立迁移账号下执行迁移，包含建表、外键、唯一索引和不可变触发器；运行账号不能修改/删除映射，也不能删除/清空计数。
- Linux生产环境应启用并检查系统NTP/chrony/systemd-timesyncd等实际使用的同步服务，保存同步状态及偏移证据；不得只因安装服务便宣称已同步。应用高水位门禁不能替代服务器NTP验收。
- 不提供后台手动改时间或重置流水入口。部署和备份恢复须一并保留订单、映射、计数；不得将计数回滚到已发号之前。
- 当前已实现持久化高水位发号门禁、时钟恢复后的迁移测试和故障回归；生产NTP源/偏移/回拨证据及恢复后不复用仍属于P7验收。
- 生成/落库、支付宝及微信新单的下单、通知、查询、关单和退款编号已完成本地切换验证；商店、后台订单、退款、财务核查及交易通知已统一显示业务订单号，历史订单无业务号时回退原号。0018只追加绑定固定新单支付编号；此前已使用旧编号的订单继续原号，不根据展示字段强行改写。内部接口路径和关联仍使用内部ID。微信待核对业务等仍按重构计划继续，真实平台及生产验收归P7。
