# 软件更新分发与后台管理实施方案

本文将 [V2 原始方案](software-update-distribution-v2.md) 扩展到电脑软件和 Android 软件。以下内容是待实施设计。现有门户已具备多商品管理、商品价格与购买开关、按账号和软件隔离的授权，以及网站自身的系统升级功能。

## 1. 商品管理入口

在现有 `/admin/products` 商品列表中显示支持的平台、各平台最新版本、运营模式和公测截止时间。保留原有商品介绍、图片、CNY/USD 定价和购买开关。每个商品的详情页增加以下区块：

| 区块 | 管理员操作 |
| --- | --- |
| 平台与版本 | 选择 Windows、macOS、Linux、Android 中实际支持的平台。按平台、架构和版本维护安装包或压缩包。 |
| 下载渠道 | 对每个版本文件添加任意数量的渠道，可新增、编辑、调序、启停或移除。首版界面和数据模型不设固定渠道数量，也不限制每个地区只有一主一备。 |
| 运营与试用 | 单独为每个软件设置公测开始、截止时间、截止后的免费或收费模式，以及正式期试用开关和天数。 |
| 发布记录 | 查看操作人、时间、变更前后值和原因。敏感提取码及短期签名链接不写入审计。 |

商品管理沿用 `products.manage`，写入沿用现有管理员会话、CSRF 和审计机制。用户管理 `/admin/users` 沿用现有的多软件授权详情与权限，展示用户对每个商品的购买来源、公测参与情况及试用期限。网站自身的 GitHub/systemd 升级仍在 `/admin/upgrade`。参见 [多软件授权接入](multi-software-licensing.md) 和 [门户升级包格式](online-update-package-format.md)。

## 2. 软件版本、文件与下载渠道

| 数据对象 | 建议字段与约束 |
| --- | --- |
| 商品 | 沿用 `portal_products.code` 作为稳定商品标识。同一商品可关联多个平台，各平台共享该商品的授权。 |
| 平台版本 | 商品、平台、递增的整数版本号、展示版本、更新说明、状态和发布日期。同一商品的平台版本号唯一。Android 整数版本号使用 APK 的 `versionCode`，电脑端由构建清单提供整数版本号。 |
| 版本文件 | 版本、架构、格式、文件名、字节数、SHA-256。同一版本可包含多个文件。Android 额外记录包名和签名证书指纹。 |
| 下载渠道 | 所属文件、名称、供应商、网盘或直链、适用地区、顺序、HTTPS 地址、可选提取码、启用状态、最近检查与实测结果。每条渠道独立管理。 |
| 更新策略 | 按商品及平台保存最低支持版本和配置版本。按架构下发时，强制升级必须覆盖所有仍受支持的架构。 |

管理员从构建清单导入文件元数据，也可手工录入。SHA-256 必填，服务端校验其为 64 位十六进制并统一为小写。后台、账号中心和客户端按具体文件展示 **SHA-256、文件名与大小**，提供复制哈希和校验说明。用户应比对自己下载的对应平台文件。Windows 可用 `Get-FileHash -Algorithm SHA256 -LiteralPath '文件路径'`，Linux 可用 `sha256sum`，macOS 可用 `shasum -a 256`。Android 可由客户端通过系统文件选择器读取文件并计算哈希。

一个文件挂多个渠道时，各渠道必须提供字节一致的文件。如果架构、安装格式或实际字节不同，登记为不同文件并分别记录 SHA-256。已发布文件的哈希、大小和平台架构固定。更换发布文件时提高版本号，同一文件的镜像 URL 可独立维护。SHA-256 用于比对文件完整性，Android 覆盖安装仍需验证签名证书和包名，电脑安装程序沿用各平台的签名验证。

渠道按地区和显示顺序下发，最后追加适用全球的渠道，并允许用户选择备用来源。可挂载任意多个已核验的服务商、网盘、对象存储和自有 HTTPS 下载域名。增加新域名时先在服务端管理允许列表中验证并登记。后台的连通性检查只说明地址可访问，发布前仍需在目标地区和设备实测下载并核对 SHA-256。门户保存清单与渠道元数据，文件由下载站直接提供。

发布流程为草稿、实测通过、发布、撤回。发布时每个文件至少有一条通过实测的启用渠道。提高最低支持版本时，确认目标版本对各受支持架构可安装，并有独立的备用来源。某条渠道失效时允许单独停用。全部来源失效时显示恢复入口，保留登录、重试和客服路径。撤回坏包后重新核对最低版本门槛，已装坏包的用户通过更高版本修复。

## 3. 每个软件的公测截止与权益

- 管理员在商品的「运营与试用」表单设置公测截止日期、时间和时区。表单同时显示保存后的本地时间与 UTC，服务端统一存 UTC。到达截止时刻即进入正式模式。同一商品的各个平台共用该商品的公测截止时间，其他商品独立。
- 公测开始前可保存草稿。公测期间，管理员可提前或推迟截止时间、修改截止后的模式和试用参数。保存时携带配置版本，事务内判断公测仍有效。提前转正式使用同一截止流程。截止后锁定该轮生效配置，单个用户延期走客服补偿。
- 服务端按当前时间推导阶段，保留该轮最终截止时刻和试用参数快照。公测参与者进入正式收费后，其试用以该截止时刻起算，晚登录也沿用原起点。其余用户首次显式领取收费功能试用时起算。登录、浏览和下载不触发试用。
- 永久授权优先。关闭试用只停止新发放。收费、免费模式往返切换时保留既有试用起止时间，免费期间继续计时。领取试用按账号与商品进行事务内去重，重复请求返回同一记录。
- 沿用现有支付成功履约和退款撤权规则。上线迁移前核对现有正式授权、订单来源和试用期限，按账号与商品去重，保留已撤权记录和原到期时间。新试用记录与原授权表之间由同一权益裁决服务统一读取，避免两个入口分别发放试用。

## 4. 客户端和用户侧

沿用 V2 原方案拟议的 `POST /api/v1/products/{product_code}/bootstrap`。请求携带受支持的平台及架构，响应独立返回权益和匹配平台的更新数据。更新数据包含最新版本号、最低支持版本、发布说明及文件列表。每个文件返回 `file_name`、`architecture`、`file_size`、`sha256` 和可用渠道。无匹配版本时返回空发布信息。接口使用 `Cache-Control: no-store`。

账号中心列出已发布的商品和版本下载。所有会话有效的注册用户都可查询和下载已发布更新，使用权限由授权单独裁决。现有公开商品页和现有下载链接保留其原有行为，账号下载区与客户端接口按新规则控制。既有桌面客户端登录与心跳接口继续兼容，接入新接口的电脑和 Android 客户端在登录后分别读取本机版本并比较。最新或更高版本保持静默，可选更新允许稍后处理，强更提供备用渠道、客服和退出入口。

## 5. 开发顺序与验收

1. **后台和数据**：同一商品可同时配置电脑和 Android，录入不同文件哈希。为同一文件添加三条及以上渠道，验证可独立排序、停用和替换。旧商品、订单和正式授权正常读取。
2. **下载闭环**：用同一注册账号在电脑和 Android 查询，确认只收到匹配平台与架构的文件，各渠道实际下载的文件与公开 SHA-256 一致。验证某个渠道故障会保留其他渠道，门户不传输文件正文。
3. **公测和试用**：两个软件分别设置截止时间，覆盖时区转换、截止前后、晚登录、提前结束、并发领取和收费免费反复切换，确认权益和试用互不串用。
4. **发布与恢复**：确认坏包撤回、提高和降低最低版本、全部渠道失效、发布后换镜像、已安装坏包的高版本修复都可操作且有记录。
