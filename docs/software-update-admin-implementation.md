# 软件更新分发与后台管理实施方案

本文将 [V2 原始方案](software-update-distribution-v2.md) 扩展到电脑软件和 Android 软件。以下内容是待实施设计。现有门户已具备多商品管理、商品价格与购买开关、按账号和软件隔离的授权，以及网站自身的系统升级功能。

## 1. 商品管理入口

在现有 `/admin/products` 商品列表中显示支持的平台、各平台最新版本、运营模式和公测截止时间。保留原有商品介绍、图片、CNY/USD 定价和购买开关。每个商品的详情页增加以下区块：

| 区块 | 管理员操作 |
| --- | --- |
| 平台与版本 | 选择 Windows、macOS、Linux、Android 中实际支持的平台。按平台、架构和版本维护安装包或压缩包。 |
| 下载渠道 | 对每个版本文件添加任意数量的渠道，可新增、编辑、调序、启停或移除。首版界面和数据模型不设固定渠道数量，也不限制每个地区只有一主一备。 |
| 运营与试用 | 每个上架商品各自设置公测开始、截止时间、截止后的免费或收费模式，以及正式期试用开关和天数。 |
| 发布记录 | 查看操作人、时间、变更前后值和原因。敏感提取码及短期签名链接不写入审计。 |

商品管理沿用 `products.manage`，写入沿用现有管理员会话、CSRF 和审计机制。用户管理 `/admin/users` 沿用现有的多软件授权详情与权限，展示用户对每个商品的购买来源、公测参与情况及试用期限。网站自身的 GitHub/systemd 升级仍在 `/admin/upgrade`。参见 [多软件授权接入](multi-software-licensing.md) 和 [门户升级包格式](online-update-package-format.md)。

## 2. 软件版本、文件与下载渠道

| 数据对象 | 建议字段与约束 |
| --- | --- |
| 商品 | 沿用 `portal_products.code` 作为稳定商品标识。同一商品可关联多个平台，各平台共享该商品的授权。 |
| 平台版本 | 商品、平台、递增的整数版本号、展示版本、更新说明、状态和发布日期。同一商品的平台版本号唯一。Android 整数版本号使用 APK 的 `versionCode`，电脑端由构建清单提供整数版本号。 |
| 版本文件 | 版本、架构、格式、文件名、字节数、SHA-256。同一版本可包含多个文件。Android 额外记录包名和签名证书指纹。 |
| 下载渠道 | 所属文件、名称、供应商、网盘或直链、适用地区、顺序、HTTPS 地址、可选提取码、启用状态、最近检查与实测结果。每条渠道独立管理。 |
| 更新策略 | 按商品及平台保存最低支持版本和配置版本。按架构下发时，强制升级必须覆盖所有仍受支持的架构。 |

管理员从构建清单导入文件元数据，也可手工录入。SHA-256 必填，服务端校验其为 64 位十六进制并统一为小写。后台、账号中心和客户端按具体文件展示 **SHA-256、文件名与大小**，提供复制哈希和校验说明。用户应比对自己下载的对应平台文件。Windows 可用 `Get-FileHash -Algorithm SHA256 -LiteralPath '文件路径'`，Linux 可用 `sha256sum`，macOS 可用 `shasum -a 256`。Android 可由客户端通过系统文件选择器读取文件并计算哈希。

一个文件挂多个渠道时，各渠道必须提供字节一致的文件。如果架构、安装格式或实际字节不同，登记为不同文件并分别记录 SHA-256。已发布文件的哈希、大小和平台架构固定。更换发布文件时提高版本号，同一文件的镜像 URL 可独立维护。SHA-256 用于比对文件完整性，Android 覆盖安装仍需验证签名证书和包名，电脑安装程序沿用各平台的签名验证。

渠道按地区和显示顺序下发，最后追加适用全球的渠道，并允许用户选择备用来源。可挂载任意多个已核验的服务商、网盘、对象存储和自有 HTTPS 下载域名。增加新域名时先在服务端管理允许列表中验证并登记。后台的连通性检查只说明地址可访问，发布前仍需在目标地区和设备实测下载并核对 SHA-256。门户保存清单与渠道元数据，文件由下载站直接提供。

发布流程为草稿、实测通过、发布、撤回。发布时每个文件至少有一条通过实测的启用渠道。提高最低支持版本时，确认目标版本对各受支持架构可安装，并有独立的备用来源。某条渠道失效时允许单独停用。全部来源失效时显示恢复入口，保留登录、重试和客服路径。撤回坏包后重新核对最低版本门槛，已装坏包的用户通过更高版本修复。

## 3. 每个商品软件独立设置公测截止时间

- 管理员在商品的「运营与试用」表单设置公测截止日期、时间和时区。表单同时显示保存后的本地时间与 UTC，服务端统一存 UTC。后台以商品编号（`product_code`）保存和读取公测配置。到达截止时刻时，仅对应商品进入其预设的正式模式。同名或同系列软件、电脑版与 Android 版只要分别上架，就在各自的商品详情中单独设置截止时间。修改其中一项不会影响其他商品。
- 公测开始前可保存草稿。公测期间，管理员可提前或推迟截止时间、修改截止后的模式和试用参数。保存时携带配置版本，事务内判断公测仍有效。提前转正式使用同一截止流程。截止后锁定该轮生效配置，单个用户延期走客服补偿。
- 服务端按当前时间推导阶段，保留该轮最终截止时刻和试用参数快照。公测参与者进入正式收费后，其试用以该截止时刻起算，晚登录也沿用原起点。其余用户首次显式领取收费功能试用时起算。登录、浏览和下载不触发试用。
- 永久授权优先。关闭试用只停止新发放。收费、免费模式往返切换时保留既有试用起止时间，免费期间继续计时。领取试用按账号与商品进行事务内去重，重复请求返回同一记录。
- 沿用现有支付成功履约和退款撤权规则。上线迁移前核对现有正式授权、订单来源和试用期限，按账号与商品去重，保留已撤权记录和原到期时间。新试用记录与原授权表之间由同一权益裁决服务统一读取，避免两个入口分别发放试用。

## 4. 客户端和用户侧

沿用 V2 原方案拟议的 `POST /api/v1/products/{product_code}/bootstrap`。请求携带受支持的平台及架构，响应独立返回权益和匹配平台的更新数据。更新数据包含最新版本号、最低支持版本、发布说明及文件列表。每个文件返回 `file_name`、`architecture`、`file_size`、`sha256` 和可用渠道。无匹配版本时返回空发布信息。接口使用 `Cache-Control: no-store`。

账号中心列出已发布的商品和版本下载。所有会话有效的注册用户都可查询和下载已发布更新，使用权限由授权单独裁决。现有公开商品页和现有下载链接保留其原有行为，账号下载区与客户端接口按新规则控制。既有桌面客户端登录与心跳接口继续兼容，接入新接口的电脑和 Android 客户端在登录后分别读取本机版本并比较。最新或更高版本保持静默，可选更新允许稍后处理，强更提供备用渠道、客服和退出入口。

## 5. 客户端版本上报与活跃度

电脑和 Android 客户端从正在运行的构建读取 `version_code` 和 `version_name`。登录时只发送认证、授权及定位记录必需的字段。登录成功后，客户端读取服务器保存的版本，与本机比较，首次缺少记录或版本变化时才补报。通过网站会话接入的客户端在认证后的商品 `bootstrap` 中读取保存值。软件版本由客户端自报，用于运营统计。

新增 `portal_product_user_activity`，以 `(user_id, product_code, platform)` 为唯一键。保存 `last_client_login_at`、`last_version_reported_at`、`version_code`、`version_name`、`architecture` 和软件版本的 `revision`。旧客户端未提供平台时记为 `unknown`，没有版本信息时保留上次已知版本及其上报时间。仅在成功认证的客户端登录或登录后的首次商品初始化时更新，使用服务端 UTC 时间；登录失败、网页浏览和下载不刷新客户端活跃时间。首版每个平台只保留一份最近记录。

在 `/admin/users` 的多软件详情展示各平台最后登录时间、最后上报版本和上报时间。列表支持按软件、平台、版本和最近登录时间过滤。默认把该商品最近 30 天没有客户端登录的用户归为「近期未登录」，从未有记录的另列为「暂无客户端记录」。同一商品跨平台查看时，取各平台最后登录时间的最大值。这里衡量的是客户端登录活跃度，离线使用和长期未重新登录的用户无法由此准确识别。

### 5.1 软件版本与设备信息的按需同步

新增 `portal_product_user_environment` 表，以 `(user_id, product_code, platform, device_type)` 为唯一键，保存每种设备类型最近一次有效上报。Android 手机与 Android 头显分别保存。数据库另存服务器生成的 `reported_at`（UTC）和并发更新用的 `revision`。

1. **登录并读取**：客户端发送认证、授权及定位记录必需的字段，包括支持比较时的平台和设备类别。服务端认证成功后，在同一响应中返回该用户、商品、平台的已保存软件版本，以及匹配设备类别的设备资料。两部分各带自己的 `revision`，无记录时返回空值。使用网站会话的客户端通过认证后的商品 `bootstrap` 读取相同数据。
2. **客户端比较**：将本机软件版本和设备资料分别与服务器保存值做标准化比较。两者都相同时跳过上传。首次有值或发现变化时，通过同一次 `POST /api/v2/client/environment` 补报变化的部分，并携带对应的 `revision`。软件版本的整数与展示值作为一组提交。未读取到的设备字段省略。
3. **保存与并发**：服务端从会话确定用户和商品，校验平台、设备类别和字段，再分别检查 `revision` 并更新变化的部分。发生冲突时返回当前资料，客户端重新比较。软件版本未变时保留 `last_version_reported_at`，设备资料未变时保留 `reported_at`。每次成功登录仍刷新 `last_client_login_at`。旧客户端可省略这些统计字段，补报失败可独立重试。认证、授权及需要即时判断本机版本的业务接口仍按各自协议提交必需字段。

| 字段 | 适用范围 | 举例 |
| --- | --- | --- |
| `device_type` | 设备类别 | `desktop`、`headset`、`phone`、`tablet`、`unknown` |
| `os_name` | 系统名称 | Windows 10、Windows 11、Ubuntu、macOS、Android |
| `os_version` | 系统版本或发布号 | 22H2、24H2、24.04、15.1、14 |
| `os_build` | 可选的系统构建号 | Windows 构建号 `26100.1742` |
| `gpu_model` | 电脑端可选，优先记录软件实际选用的 GPU | NVIDIA GeForce RTX 4060 |
| `android_api_level` | Android 设备可选，整数 | `34` |
| `device_model` | 头显型号，也可用于 Android 手机或平板 | Meta Quest 3 |

后台把系统名称和版本组合显示，例如「Windows 11 24H2」。保留已有的软件版本列，另显示系统、显卡或头显型号，以及设备信息的最后上报时间。支持按商品、平台、系统版本、显卡和头显型号筛选。Android 头显显示 Android 版本和型号。无法确认 Windows 的发布号时可只上报构建号，Linux 可上报发行版及其版本。

客户端仅在读取到对应值时填写。字段为空、无法识别或旧客户端未上报时，按缺省处理，成功登录流程照常。类型、长度和枚举由服务端校验。设备信息仅用于兼容性与运营统计，不作为鉴权依据，也不收集设备序列号、MAC 地址或广告标识。验收覆盖 Windows 10、Windows 11、Linux、macOS 和 Android 头显，并检查 Android 手机与头显的记录不会互相覆盖。

### 5.2 心跳负载调节

在现有后台系统设置中增加「客户端心跳策略」，限 `settings.manage` 管理。首版按站点统一设置心跳间隔和错峰百分比，默认 900 秒与 10%，保存前校验范围，记录操作人及变更前后值。登录和心跳响应读取最新有效策略。后台展示当前生效值，提供恢复默认操作。

支持管理员按负载人工调节，例如从 900 秒调为 1800 秒。自动调节可在接入负载监控后接入同一策略服务，采用持续窗口、上下限和冷却时间，避免短时波动造成客户端频繁改频。请求率、限流率及失败率可用于观察效果。验收覆盖修改策略后下一次心跳生效、错峰、配置缺省、限流退避，以及凭证仍按原期限失效。详见 [客户端编程规格](client-login-entitlement-update-spec.md)。

## 6. 开发顺序与验收

1. **后台和数据**：同一商品可同时配置电脑和 Android，录入不同文件哈希。为同一文件添加三条及以上渠道，验证可独立排序、停用和替换。旧商品、订单和正式授权正常读取。
2. **下载闭环**：用同一注册账号在电脑和 Android 查询，确认只收到匹配平台与架构的文件，各渠道实际下载的文件与公开 SHA-256 一致。验证某个渠道故障会保留其他渠道，门户不传输文件正文。
3. **公测和试用**：给同系列的电脑版和 Android 版分别建立商品，设置不同截止时间。验证电脑版到期时 Android 版仍在公测，调整其中一个商品的时间后另一个保持原计划。再覆盖时区转换、晚登录、并发领取和免费收费切换，确认权益和试用按商品隔离。
4. **发布与恢复**：确认坏包撤回、提高和降低最低版本、全部渠道失效、发布后换镜像、已安装坏包的高版本修复都可操作且有记录。
5. **客户端活跃度**：验证成功登录更新正确商品及平台的数据，旧客户端仍可登录，缺省版本保留最后一次有效上报。验证失败登录和网页访问不计入，并区分近期未登录与暂无记录。
6. **软件版本和设备资料按变化上报**：首次登录按缺失项补报，连续两次用相同版本和设备环境登录时只刷新最后登录时间。只升级软件时仅补报版本，单独更换系统或显卡时仅补报变化的设备字段，两类同时改变时合并在一次请求中。覆盖降级重装、旧客户端缺省、并发冲突和 Android 手机与头显分别取值。
